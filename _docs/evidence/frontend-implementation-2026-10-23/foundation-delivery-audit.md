## Delivery scope and dependency boundary

The live dependency order is `#61 → #67 → #68 → downstream consumers`. #61's accepted report is document-only; its closed state does not accept #67 or #68. The #67 issue itself allows ordinary compatible runtime/tooling choices by the technical owner, but its live workflow text still says the runtime/tooling prerequisite record is unfinished. The current package/README record the choices; the Orchestrator should state explicitly that this resolves the readiness condition when updating #67.

The bounded ownership manifests are:

- **#67 runtime/harness:** `frontend/package.json`, `frontend/package-lock.json`, `frontend/.env.mock`, `frontend/.gitignore`, `frontend/README.md`, `frontend/index.html`, `frontend/vite.config.ts`, `frontend/tsconfig.json`, `frontend/tsconfig.app.json`, `frontend/tsconfig.node.json`, `frontend/vite-env.d.ts`, `frontend/playwright.config.ts`, `frontend/playwright.real.config.ts`, `frontend/src/main.tsx`, `frontend/src/app/RuntimeFailure.tsx`, `frontend/src/services/bootstrap.ts`, `frontend/src/test/setup.ts`, `frontend/e2e/runtime-smoke.spec.ts`, `frontend/e2e/helpers/diagnostics.ts`, and `frontend/e2e-real/adapter-unavailable.spec.ts`. `frontend/src/i18n/messages.ts` contains runtime-failure copy alongside broad product copy; treat it as a shared integration path rather than pulling unrelated translations into a standalone #67 commit.
- **#68 facade contract/enforcement:** `frontend/src/services/contracts.ts`, `frontend/src/services/index.ts`, `frontend/tests/services/adapter-contract.ts`, `frontend/tests/services/adapter-contract.test.ts`, `frontend/tests/services/title-and-boundary.test.ts`, and the shared `frontend/tests/services/test-support.ts` required by the contract test.
- **Required implementation dependencies, owned by adjacent service/domain work:** `frontend/src/services/index.ts` imports `indexeddb.ts`, `browser-media.ts`, `mock-credits.ts`, `mock-identity.ts`, `mock-operations.ts`, `mock-preparation.ts`, `mock-previews.ts`, `mock-projects.ts`, `mock-recording.ts`, `mock-results.ts`, `mock-workspace.ts`, and `mock-store.ts`. Keep these under their owning service/domain issues rather than expanding #68 into every mock implementation.

There is an integration constraint: #67's `main.tsx` imports `App`, and its bootstrap imports the #68 service factory; `App` and the facade factory in turn import downstream screens and service modules. Therefore a standalone #67-only commit cannot build from a clean checkout of its manifest. Preserve the issue ownership above, but deliver the necessary dependency cohort together (or ensure its owning tasks are already in the base) before claiming a clean build. Keep `package.json`/lock ownership with #67 and the shared `messages.ts` path with its existing owner.
